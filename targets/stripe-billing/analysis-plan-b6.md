# Analysis plan: stripe-billing, holdout batch 6 (staged)

Pre-registered on 2026-10-14 (after batch 5) and committed before any fixture of the batch is recorded (rule 3 of
`docs/verification.md`). Nothing below may change once the first `hold-b6-` fixture exists; a
change means a new batch with a new seed.

## The batch

- **Probes:** 473, generated by `wideProbesV2` in `probes.ts` from the `hold-b6` seed in
  `holdout-seed.json`, drawn when this plan was written, in three consecutive stages:
  `hold-b6-s1-001` to `hold-b6-s1-158`, `hold-b6-s2-001` to `hold-b6-s2-158`, and
  `hold-b6-s3-001` to `hold-b6-s3-157`. Every `hold-` probe is holdout by construction; the seed
  file never enters a builder sandbox.
- **Distribution:** `WIDE_DISTRIBUTION_V2`, the same as batches 3 to 5. Batches 4 and 5 each supported
  "below 1 % at 95 %" with one failure (`measurements.md`); this batch measures the clone improved
  since, and only it can support the 99 % claim on this distribution.
- **Recording:** once, with `npm run record`, Stripe test mode, each probe twice for noise.

## The claim and the decision rule

- **Claim under test:** on `WIDE_DISTRIBUTION_V2`, the clone's per-case divergence rate is below
  1 %.
- **A case passes** when `npm run verify` finds no blocking difference under `policy.json` as
  locked at the measurement commit. A crash counts as a failure.
- **Sequential scoring:** `npm run verify stripe-billing -- --sequential hold-b6 --max-failures 1`
  scores stage 1, then 2, then 3, and stops as soon as the failures so far exceed 1. Stopping only
  on failure leaves the decision below unchanged; a stopped run rejects the claim, and the stages
  never scored are not spent.
- **Decision**, with k failures over the stages scored (one-sided exact Clopper-Pearson bounds):
  - all three stages scored and k = 0: "below 1 % at 99 % confidence" (bound 0.97 %);
  - all three stages scored and k = 1: "below 1 % at 95 % confidence" (bound 0.999 %);
  - k ≥ 2 (scoring stops as soon as this happens): the claim is not supported; report "k of n"
    for the n cases scored, and which stages remain fresh.
- **Reported apart, no claim:** the easy share (Stripe errors, changes that change nothing).

## The measurement

- **Measured clone:** the clone measured on batch 5 (v4), after one more builder pass in the agent
  container that may use every dev fixture (including the v5 probes: the DSC-07 area of batches 4
  and 5, the seven designs of the batch 4 analysis, mutation holes of v4 and the v4 builder's
  unpinned choices), and never sees batch 6. Frozen at a commit before batch 6 is scored.
- **One look per stage:** the sequential run above, once. Its line in `verify/runs.jsonl` names
  the stages scored; the fidelity report and the reliability card say which stages stay fresh.
- **Afterwards:** the stages scored are spent; the result goes into `measurements.md`, whatever it
  is.
