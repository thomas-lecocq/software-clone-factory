# Analysis plan: stripe-billing, holdout batch 2

Pre-registered on 2026-10-01 and committed before any fixture of the batch is recorded (rule 3 of
`docs/verification.md`). Nothing below may change once the first `hold-b2-` fixture exists; a change
means a new batch with a new seed.

## The batch

- **Probes:** `hold-b2-001` to `hold-b2-473`, generated by `wideProbes` in `probes.ts` from the
  `hold-b2` seed in `holdout-seed.json`, drawn when this plan was written. Every `hold-` probe is
  holdout by construction (`splitOf`); the seed file matches `holdout-*`, so it never enters a
  builder sandbox and the batch does not exist there.
- **Distribution:** `WIDE_DISTRIBUTION` in `probes.ts`, the same as batch 1 (`analysis-plan.md`) and
  as the `wide-` and `wide2-` probes the builder may train on (their dev share). Same slice as the
  original fixtures: a mid-cycle change previewed with `create_preview`, widened to 1 to 3 items,
  monthly or yearly prices, 0 to 2 coupons, quantities 1 to 10, starts across a year and changes
  across the whole first period.
- **Recording:** once, with `npm run record`, Stripe test mode, each probe twice for noise. Recorded
  noise is ignored per path and listed in the report.
- **Size:** 473, the smallest batch that still supports "below 1 % at 95 %" with one failure. With
  none, the bound at 99 % is 1 − 0.01^(1/473) = 0.97 %.

## The claim and the decision rule

- **Claim under test:** on this distribution, the clone's per-case divergence rate is below 1 %.
- **A case passes** when `npm run verify` finds no blocking difference under `policy.json` as locked
  at the measurement commit. A crash counts as a failure. Any change to `policy.json` between this
  plan and the measurement is listed in the fidelity report.
- **Decision**, with k failures out of 473 and one-sided exact (Clopper-Pearson) upper bounds:
  - k = 0: "below 1 % at 99 % confidence" (bound 0.97 %);
  - k = 1: "below 1 % at 95 % confidence" (bound 0.999 %), not at 99 %;
  - k ≥ 2: the claim is not supported; report "k of 473" and both bounds.

  | k            | 0      | 1       | 2      | 3      |
  | ------------ | ------ | ------- | ------ | ------ |
  | bound (95 %) | 0.63 % | 0.999 % | 1.33 % | 1.63 % |
  | bound (99 %) | 0.97 % | 1.40 %  | 1.77 % | 2.11 % |

## The measurement

- **Measured clone:** the clone measured on batch 1 (`measurements.md`), after one more builder pass
  in the agent container. That pass may use everything learnt from the spent batch 1
  (`analysis/batch1-failures.md`) and the dev probes added since; it never sees batch 2. The clone
  is frozen at a commit before batch 2 is scored.
- **One look:** `npm run verify stripe-billing -- --split holdout` runs once on that commit for this
  batch (it also rescores the spent batch 1, which carries no claim). Its line in
  `verify/runs.jsonl` (commit, lock, clean tree) is the result. A run that stops before scoring
  (integrity check, clone that does not start) may be repeated; a scored run counts.
- **Afterwards the batch is spent.** Failures are analysed by a session that did not build the clone
  and may lead to fixes, but any later claim on this slice needs a new batch and a new seed.

## Reported, not claimed

- Per-rule pass counts on the batch, the hash-split holdout (original fixtures, `wide-`, `uf-` and
  `x-` probes) and the UI results, as counts with their bounds, without a threshold.
- Out of scope for this claim: the portal UI, the slice 2 lifecycle, live mode (test mode is assumed
  equal), other currencies and locales, and every input outside the distribution above.
