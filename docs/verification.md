# Verification standard

What makes a clone "verified" rather than "plausible". Every agent and script in the factory
follows it. Read it before writing any harness component or target.

## The five rules

1. **Fixtures are the frozen evaluator.** A fixture is a probe's input and the target's real,
   recorded output. Fidelity is only ever a comparison of the clone's output with a fixture: no
   fixture, no claim. Fixtures are recorded before the clone is built, and hashed together with the
   diff policy and the code that drives the evaluation (`fixtures.lock`). `verify` checks the
   hashes, and that the lock equals the committed one, before every run.
2. **Agents never write the score.** Only `verify` produces the scorecard. Implementer agents work
   in a sandbox copy that holds no holdout, no audit material, no secrets and no git history; only
   their clone is copied back. A guard hook inside the sandbox is a second line, not the guarantee.
3. **Every claim has a scorecard line.** Fidelity is stated as "N of M fixtures pass", with the
   holdout reported apart from dev, its confidence bound given, and the method and level named.
   Behaviour without a fixture is reported as unknown, never as matching.
4. **Gaps are a first-class artefact.** `GAPS.md` lists every known divergence: what the target
   does, what the clone does, whether a fixture measures it, and why it was left.
5. **Failures are memory.** A change that breaks a fixture is logged in `targets/<t>/failures.jsonl`
   (`what`, `fixture_broken`, `root_cause`, `retry_if`), with the root cause written by a session
   that did not make the change. The builder reads it before proposing.

## What "verified clone" means

- **Behavioural:** the recorded fixtures pass. Not "looks the same".
- **Seedable and resettable:** every run starts from a known state; `POST /__reset` restores it,
  and the same probe run twice after a reset gives identical output.
- **Differential:** the same code drives the target and the clone; outputs are compared field by
  field, with a per-field policy (exact, normalised, ignored), each exception justified in one line.
- **Screens:** a UI fixture is an action trace plus normalised state (visible text, enabled or
  disabled controls, requests fired), never a raw capture. Visual differences are measured by
  deterministic diffs; an LLM may triage flagged differences, never score them.

## Measurement

- **Dev and holdout.** Dev fixtures are for building; holdout fixtures are for proving. The builder
  never sees holdout cases. A holdout that has driven a decision is spent; the next clean measure
  needs a fresh batch.
- **Sized from the claim.** With zero failures in n random draws, the one-sided 95 % upper bound on
  the divergence rate is 1 − 0.05^(1/n): about 3/n. A "below 1 %" claim needs at least 299 clean
  cases. The bound only holds over the distribution the probes were drawn from, which is stated.
- **Pre-registered.** Before recording a holdout batch, its distribution, size, threshold and
  stopping rule are committed in `targets/<t>/analysis-plan.md`.
- **Logged.** Every `verify` run is appended to `verify/runs.jsonl` (time, splits, results, lock,
  commit, sandbox), so the number of looks at a holdout is a fact.

## Process rules

- **Record before building.** Coverage per rule is generated by `verify` (`verify/coverage.md`).
- **Re-recording** an existing fixture needs evidence that the target changed or the recording was
  wrong (replaying the original shows it), never "the clone does not pass". It happens in its own
  commit, with the fixture, the reason and the old and new hash.
- **Relocking** after a deliberate evaluator change: `npm run relock <t> -- --reason ...`, then
  commit. Relock refuses to absorb a changed fixture.
- **Audits** are run by fresh sessions that built nothing, from the committed prompts in `audit/`;
  auditors themselves are measured on planted defects.

## When something is not verified

Write exactly: "Not covered by a fixture; behaviour inferred from <source>; unverified."
